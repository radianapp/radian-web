Jalan yang sama, setiap kaliThe same road, every time

Setiap sistem yang saya bangun melewati lima pemberhentian. Bukan karena saya kaku, tapi karena urutan inilah yang membuat hasilnya bisa dirawat orang lain, lama setelah saya pindah ke proyek berikutnya.

Every system I build passes through five stops. Not because I'm rigid, but because this order is what lets other people maintain the result long after I've moved on to the next project.

1Bab 1 dari 5Chapter 1 of 5

Ide yang masih berantakanAn idea that's still messy

Semua dimulai dari coretan: masalah siapa yang mau diselesaikan, apa yang sudah pernah dicoba, dan apa yang belum jelas. Di tahap ini saya sengaja membiarkan ide tetap berantakan, asalkan tertulis. Ide yang hanya ada di kepala tidak bisa didiskusikan.

It starts with scribbles: whose problem we're solving, what's been tried before, and what's still unclear. At this stage I let ideas stay messy, as long as they're written down. An idea that only lives in someone's head can't be discussed.

HasilOutput
Catatan brainstorming dan daftar pertanyaan terbukaBrainstorm notes and a list of open questions

2Bab 2 dari 5Chapter 2 of 5

Kontrak sebelum kodeA contract before code

Sebelum satu baris kode ditulis, saya menulis PRD dan user story: apa yang dibangun, untuk siapa, dan kapan sebuah fitur dianggap selesai. Dokumen ini jadi kontrak antara bisnis dan tim teknis, jadi tidak ada yang kaget saat demo.

Before a single line of code, I write the PRD and user stories: what we're building, for whom, and when a feature counts as done. That document becomes the contract between business and engineering, so nobody is surprised at the demo.

HasilOutput
PRD dan user story lengkap dengan kriteria penerimaanA PRD and user stories with acceptance criteria

3Bab 3 dari 5Chapter 3 of 5

Keputusan yang punya alasanDecisions with a paper trail

DRF atau yang lain? Satu database atau dua? Setiap pilihan arsitektur saya catat sebagai ADR, lengkap dengan alternatif yang ditolak dan alasannya. Enam bulan kemudian, siapa pun bisa membaca kenapa sistemnya dibangun seperti ini.

DRF or something else? One database or two? I record every architecture choice as an ADR, including the alternatives we rejected and why. Six months later, anyone can read why the system is built the way it is.

4Bab 4 dari 5Chapter 4 of 5

Fondasi yang tidak dibangun ulangFoundations you don't rebuild

Wireframe menentukan alurnya, starter kit menyediakan fondasinya: struktur folder, autentikasi, konvensi penamaan, komponen UI, dan dokumentasi API. Proyek baru langsung mulai dari fitur, bukan dari halaman login yang ke sekian kalinya.

Wireframes settle the flow; a starter kit provides the foundation: folder structure, authentication, naming conventions, UI components, and API docs. A new project starts with its features, not with yet another login page.

5Bab 5 dari 5Chapter 5 of 5

Diuji, lalu dijadikan standarTested, then made the standard

QA memastikan sistemnya benar, UAT memastikan sistemnya berguna. Pola yang terbukti berhasil saya angkat jadi template dan standar tim, supaya proyek berikutnya selesai lebih cepat dari proyek ini. Di situlah cerita ini kembali ke bab pertama.

QA makes sure the system is right; UAT makes sure it's useful. Patterns that prove themselves become templates and team standards, so the next project ships faster than this one did. That's where the story loops back to chapter one.

Studi kasus: A2UI di Dasa UI v2Case study: A2UI on Dasa UI v2

Bagaimana kalau AI agent bisa menampilkan formulir, tabel, dan dialog konfirmasi, bukan cuma teks panjang? A2UI adalah protokol terbuka untuk itu: agent mengirim pesan JSON, aplikasi yang merender antarmukanya. Saya memetakan katalog A2UI ke design system Dasa UI v2, supaya hasilnya aman dan selalu sesuai brand.

What if an AI agent could show forms, tables, and confirmation dialogs instead of long paragraphs? A2UI is an open protocol for exactly that: the agent sends JSON messages and the app renders the interface. I mapped the A2UI catalog onto the Dasa UI v2 design system, so the output is safe and always on brand.

Tentang sayaAbout me

Saya Rahadian Hadi, software engineer di Indonesia yang bekerja di persimpangan software engineering dan product development. Alih-alih mengejar fitur satu per satu, saya lebih senang membangun hal-hal yang membuat fitur berikutnya lebih mudah dibuat: arsitektur, standar pengembangan, starter kit, dan dokumentasi.

I'm Rahadian Hadi, a software engineer in Indonesia working where software engineering meets product development. Instead of chasing features one at a time, I'd rather build the things that make the next feature easier: architecture, development standards, starter kits, and documentation.

Ukuran keberhasilan saya sederhana: kalau saya cuti dua minggu, tim tetap bisa jalan karena semuanya tertulis.

My measure of success is simple: if I take two weeks off, the team keeps moving because everything is written down.

“Bangun sistem yang terstandarisasi, terdokumentasi, mudah dipelihara, dan dapat digunakan kembali untuk banyak proyek.”

“Build systems that are standardised, documented, easy to maintain, and reusable across many projects.”

Pegangan saya, tapi tetap saya sesuaikan dengan proyeknyaMy rule of thumb, bent to fit each project

Beberapa kebiasaan yang sering saya pakai. Kalau proyeknya butuh cara lain, ya saya ganti.

A few habits I reach for often. If a project needs something different, I change them.

Bahasa bisnis duluBusiness words first
Saya biasanya mulai dari istilah yang dipakai tim bisnis, lalu kodenya mengikuti. Untuk proyek kecil, yang sederhana sudah cukup.I usually start from the words the business uses, and the code follows. For small projects, simple is enough.
Sepakati API di awalAgree on the API early
Kalau banyak pihak terlibat, saya tulis kontrak OpenAPI dulu. Untuk skrip sekali pakai, tidak perlu.When several parties are involved, I write the OpenAPI contract first. For a throwaway script, I don't.
Logika tidak ikut frameworkLogic stays off the framework
Saya coba pisahkan logika bisnis dari framework supaya gampang dipindah, selama pemisahannya memang terasa berguna.I try to keep business logic apart from the framework so it's easy to move, as long as the split earns its keep.
Tulis dulu, bangun kemudianWrite first, build after
Ide yang belum bisa dijelaskan dalam beberapa paragraf biasanya belum matang. Tapi kadang prototipe menjawab lebih cepat.An idea that can't be explained in a few paragraphs usually isn't ready. Sometimes a prototype answers faster, though.
Satu cara yang disepakatiOne agreed way
Saya pilih konvensi tim supaya tidak mengulang debat yang sama. Kalau ada yang mengganggu, kita ubah bareng.I pick team conventions so we don't repeat the same debate. If one gets in the way, we change it together.
Tumbuh sedikit-sedikitGrow a little at a time
Saya lebih suka sistem yang berkembang bertahap daripada rewrite besar, kecuali fondasinya memang sudah tidak layak.I prefer systems that grow step by step over big rewrites, unless the foundation really is beyond saving.
